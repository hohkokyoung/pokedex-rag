# ADR-010: The mobile app displays server values; its API types and tokens are generated

**Status:** Accepted

## Context

A Flutter app (`mobile/`) joins the website as a second client. Dart can't share the
website's TypeScript, so anything the app re-implements (rules, API types, design
tokens) is a second copy that can drift.

## Decision

- **The app computes no game rules.** It renders what the backend returns (grades,
  evolution labels, matchups, the spin guide; see ADR-009). The one lookup it does
  itself, "Hits ×2", is a filter over the served type chart, as on the website.
- **The API types are generated** with swagger_parser from a committed slice of the
  backend's OpenAPI schema (`mobile/openapi.json`, only the endpoints the app calls).
  `backend/tests/test_mobile_openapi.py` fails when that slice goes stale.
- **The design tokens are generated** from DESIGN.md's front matter
  (`tools/mobile/gen_tokens.py`). The fonts are bundled, not fetched.
- **Home network only:** plain HTTP to a user-set address, saved only after `/health`
  answers. No auth or TLS until the backend is hosted.

## Consequences

- A backend change the app depends on fails CI until `make mobile-api` is re-run.
- A token change in DESIGN.md reaches the app with `make mobile-tokens`; nothing is
  hand-copied.
- Hosting the backend later needs auth, TLS and tighter Android cleartext rules: a new
  decision.
- Details: [guides/mobile.md](../guides/mobile.md).
