# Data pipeline

All Pokémon data comes from the [PokéAPI](https://github.com/PokeAPI/pokeapi) CSV
dataset, downloaded into `data/raw/pokeapi/csv/` (git-ignored) and ingested into
Postgres. **The app never calls PokéAPI at runtime.** Sprites go to `data/sprites/`
(git-ignored) and are served by the backend at `/sprites/...`.

Every target runs on the host against the Compose DB (`localhost:5433`).

## Full build

```bash
make data
```

runs, in order: `migrate` → `ingest` → `items` → `learnsets` → `encounters` →
`enrich` → `chart` → `sprites` → `variant-sprites` → `female-sprites` → `chunks`.

| Target | Does |
|---|---|
| `migrate` | `alembic upgrade head` |
| `ingest` | core CSV ingest: 1,025 Pokémon (national dex 1–1025, `pokemon.id == dex number`), types, abilities, moves, natures, flavour text, evolutions, alternate forms (regional, Mega, Primal, Gigantamax) |
| `items` | items |
| `forms` | re-run only the alternate forms (already part of `ingest`) |
| `learnsets` | per-game learnsets (needs pokemon, forms, moves) |
| `encounters` | where to find each Pokémon, per game (data ends at Sword/Shield) |
| `enrich` | training and breeding: gender, egg groups, growth, EV yield |
| `chart` | the type-effectiveness chart |
| `ability-effects`, `move-targets` | backfills: ability short effects; move targeting for doubles |
| `flavor`, `evolutions` | rebuild dex entries (one per game) or evolution edges |
| `sprites`, `variant-sprites`, `female-sprites` | official artwork; HOME artwork for cosmetic variants; female artwork where it differs |
| `chunks` | build `profile` + `dex_entry` chunks and embed them locally (fastembed — no API key needed) |

## Changing data on a populated DB

A full `make ingest` **fails once chunks exist**: it wipes `pokemon`, and
`knowledge_chunks.pokemon_id` references it. For incremental changes use the
standalone targets (`items`, `forms`, `learnsets`, `encounters`, `ability-effects`,
`move-targets`, `flavor`, `evolutions`, `chart`, `enrich`) — they only touch their
own tables.

If you really need a full re-ingest: empty `knowledge_chunks` first, run `make
ingest` and the standalone targets, then `make chunks`.

`team_members.form_id` and `item_id` are plain integers with **no foreign keys** on
purpose: `forms` and `items` reload their tables wholesale, which FKs would block.

## Migrations

Alembic autogenerate, but the full-text `content_tsv` column on `knowledge_chunks` is
DB-managed and excluded via `include_object` in `alembic/env.py`. Check every
autogenerated migration doesn't try to drop it.
